Stress Test Report

Results from the stress-and-data-scale-validation roadmap feature, run twice on a developer laptop against fake chat and embedding providers with zero real external calls. The gateway read path holds up cleanly under spike and soak load on both runs; a real, not-yet-fixed ingestion capacity ceiling was found on the first run and confirmed still present on the second.

100% of 4,780 k6 checks passed, 0.00% HTTP error rate
1.4s p95 gateway latency under spike + soak load (threshold 3s)
527 / 2,160 documents fully indexed — the capacity ceiling, still open
5.1 / 8 CPU cores peak draw, out of this laptop's 8 threads
2.5 GiB peak container memory at the busiest single moment

Scale disclosure

Both runs used a developer laptop (Intel i7-8650U, 8 threads, 15 GB RAM), not the documented reference hardware (8 vCPU / 32 GiB RAM / 500 GB SSD). The second run seeded 180 accounts, 720 conversations, and 2,160 documents — a safe, laptop-sized fraction of the roadmap's target (100k accounts, 5M+ conversations, 1M+ documents). It exercises the exact same code paths the full-scale run would use. The roadmap's production capacity numbers cannot be claimed from this run alone — see scaling this up and what hardware this run actually needed.

Headline result

The gateway-facing read path held up cleanly under load on both runs: on the second run, 100% of 4,780 k6 checks passed, with a 0.00% HTTP error rate and p95 latency of 1.4 s (threshold 3 s) — noticeably faster than the first run's 2.41 s p95, because this run's load test started only after bulk seeding had fully finished rather than running concurrently with it. The second run also tried the fault-injection scenario first, on an idle stack, exactly as the first run's own report recommended — this fixed both mechanical blockers from before, but surfaced a different real reliability problem instead of a clean pass (see fault injection below). The ingestion capacity ceiling found on the first run is still present, unfixed, on the second.

Gateway latency under spike + soak load

The main finding: an ingestion capacity ceiling (confirmed on both runs)

This is the same capacity ceiling found on the first run, not a new one, and it is still unfixed. As a share of the corpus: 527/2,160 = 24.4% of documents finished indexing this run, versus 254/1,520 = 16.7% on the first run — a modest improvement most plausibly explained by cleaner, faster, single-batch uploading rather than any underlying fix. Kafka consumer-group lag on trialscribe.job.v1 sat at 1,324 messages across 3 partitions and was not draining, while the separate trialscribe.document.v1 upload-event topic was fully drained (lag 0) — confirming the bottleneck is specifically in job execution/retry, not event ingestion. This needs a fix-and-reverify pass before the roadmap's capacity numbers can cite this campaign as safe at target scale.

Resource ceilings

Peak resource consumption, and what hardware this run actually needed

The numbers above describe per-container limits — what each service is allowed to use. This section answers a different, more practical question: at the single busiest moment, how much did the whole stack actually draw on this laptop? Computed by summing every container's live CPU% and memory at each matching timestamp across the full campaign, then taking the maximum:

MetricPeak valueWhen / what was running
Total CPU across every container509.39% ≈ 5.09 cores of this laptop's 8102s into bulk seeding — the busiest phase of the whole campaign
Total container memory2,508.6 MiB ≈ 2.45 GiB~1 min after the k6 run finished, while the ingestion backlog was still draining
Host available memory, low point5,272 MB ≈ 5.15 GiBnever approached the 1.5 GB abort floor

At the CPU peak, kafka alone accounted for nearly half the total (242.46% ≈ 2.4 cores) — almost certainly from handling the burst of document-upload and job-retry events all 180 concurrent seed workers were producing at once — followed by auth (49.44%), ai (49.35%), jobs (49.18%), chroma (36.18%), postgres (26.27%), and gateway (24.18%). At the memory peak, kafka (797.3 MiB) and chroma (714.0 MiB) together accounted for 60% of the total — both still doing real work (log retention, collection activity) after HTTP-facing load had already stopped.

What to actually buy, if replicating this specific rehearsal

Not the aspirational 8 vCPU / 32 GiB reference-hardware target documented below — that's sized for the full 1M+ document / 10M+ vector chunk roadmap target, not this 2,160-document rehearsal. This run's actual peak draw was ~5.1 of 8 cores and ~2.5 GiB of container memory. Rounded up for headroom, that maps to roughly an 8 vCPU / 8–16 GiB compute-optimized instance — for example an AWS c6i.2xlarge / c6a.2xlarge-class box, a GCP c2-standard-8, or an equivalent 8 vCPU cloud droplet. Note this is CPU-bound, not memory-bound: at this corpus size the observed memory ceiling stayed under 3 GiB even at the campaign's busiest moment, so a high-memory instance tier would be wasted spend for reproducing this specific test — the extra RAM in the full reference-hardware target only earns its keep once the corpus actually reaches roadmap scale.

Fault injection: ran clean this time, but the results themselves are not clean

The first run's report recommended running the fault scenario first, on a freshly-seeded idle stack, before bulk seeding piles up a backlog. The second run tried exactly that — and it fixed both of the first run's blocking issues (the overlay targeting the wrong container; starvation by the ingestion backlog). The scenario ran all four phases to completion in about 2.5 minutes and produced a real circuit-breaker chart for the first time this campaign has gotten that far:

PhaseSubmittedSucceededFailed
Baseline (no fault, circuit closed)844
Faulted (rate-limited injected)808
Recovery (fault cleared, 38s wait)808

The faulted phase behaved exactly as intended. But baseline — run on a fresh stack with the circuit confirmed closed, before any fault was ever applied — still only succeeded 4/8, and recovery still failed 8/8 even after the fault was cleared and the scripted wait elapsed. A follow-up manual probe job also failed. This points to a real provider_probe reliability problem that predates and is independent of this campaign's own fault injection — reported plainly as a new open finding, not smoothed into a pass.

To scale this up on dedicated reference hardware

  1. Fix the ingestion-failure finding first — still unfixed after two runs. Reproduce with the caught exception temporarily logged, confirm or rule out the per-conversation Chroma collection theory, and re-run to verify succeeded no longer plateaus. The single most important open item across both runs.
  2. New this run: investigate the provider_probe reliability problem found during fault injection — it failed intermittently even at baseline with no fault active, and did not fully recover within a 38-second post-fault wait. Needs its own root-cause pass, separate from item 1.
  3. Re-run on the documented reference hardware (8 vCPU / 32 GiB RAM / 500 GB SSD) with the roadmap's actual targets over a multi-hour or multi-day window. That target is sized for the full-scale corpus, not for replicating this rehearsal — see peak resource consumption above for what this rehearsal itself actually needs.
  4. Raise WORKER_PROVIDER_MAX_CONCURRENCY, the auth service's CPU allocation, and the jobs/kafka CPU caps before that run — kafka alone accounted for nearly half of this run's peak aggregate CPU.
  5. Once item 2 is fixed, repeat the fault scenario under background bulk-seeding load to see whether a genuinely healthy provider_probe path opens/recovers cleanly with a large job backlog competing for the same worker capacity — that comparison still hasn't been made.

Exact reproduction commands

This is the order actually used on the second run — fault injection first, on a freshly-seeded idle stack, then bulk seeding, then k6:

./scripts.sh env
./scripts.sh install
./scripts.sh release up

# Resource sampling, across the whole campaign:
infra/stress/sample_resources.sh trialscribe-release infra/stress/results/resource-samples.csv \
  /tmp/stop-stress-sampler 5

# Tiny warm corpus, just for the fault scenario (0 documents is fine):
uv run --frozen --package trialscribe-worker python infra/stress/seed_stress_corpus.py \
  --accounts 1 --conversations-per-org 1 --documents-per-conversation 0 --concurrency 1 \
  --out infra/stress/results/seed-summary-fault.json

# Fault injection FIRST, on the still-idle stack:
uv run --frozen --package trialscribe-worker python infra/stress/run_fault_scenario.py \
  --seed-summary infra/stress/results/seed-summary-fault.json \
  --jobs-per-phase 8 --out infra/stress/results/fault-scenario.json

# THEN the full bulk seed:
uv run --frozen --package trialscribe-worker python infra/stress/seed_stress_corpus.py \
  --accounts 180 --conversations-per-org 4 --documents-per-conversation 3 \
  --min-doc-chars 6000 --max-doc-chars 9000 --concurrency 4 \
  --out infra/stress/results/seed-summary.json

# Spike + soak load:
docker run --rm --network host \
  -e BASE_URL=http://127.0.0.1:8000 \
  -v "$(pwd)/infra/stress/stress.js:/scripts/stress.js:ro" \
  -v "$(pwd)/infra/stress/results:/results" \
  grafana/k6:2.2.0 run --summary-export /results/stress-summary.json \
  /scripts/stress.js

touch /tmp/stop-stress-sampler

# Charts:
uv run --with matplotlib==3.11.2 python infra/stress/generate_stress_charts.py \
  --seed-summary infra/stress/results/seed-summary.json \
  --k6-summary infra/stress/results/stress-summary.json \
  --fault-scenario infra/stress/results/fault-scenario.json \
  --resource-csv infra/stress/results/resource-samples.csv \
  --out-dir docs/assets

./scripts.sh release down
