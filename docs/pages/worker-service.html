Service deep dive

Worker Service

The worker service is where the clinical-writing work actually happens. Other services accept requests, store state, or route traffic; the worker indexes an uploaded protocol document, searches PubMed and a shortlist of medical websites for supporting evidence, drafts an ICH M11 section with citations a reviewer can check, and assembles the finished Word export. It runs as an independent Python application and, unlike the other backend services, ships as two separate processes that share one codebase.

For a simple mental model, imagine a request desk with a back office:

  • Other services hand the worker a ticket: "index this file," "draft section 4," "check whether this protocol is ready to export."
  • The ticket is written to PostgreSQL and a Kafka queue in one indivisible step.
  • One process, the job runtime, is the only one that reads the queue and does the work.
  • A second, smaller process, the HTTP API, lets the front desk create a ticket, check its status, cancel it, or download what it produced. It never does the work itself.

Service boundary

./scripts.sh run worker starts trialscribe_worker.api.app, a FastAPI application on port 8004. It has no queue reader and no provider connections; it only reads and writes job tickets, generation attempts, usage totals, readiness snapshots, and exports already sitting in PostgreSQL or Redis. ./scripts.sh run jobs starts trialscribe_worker.runtime.main, which owns every external connection the work itself needs — PostgreSQL, Redis, Kafka, Chroma, and the configured chat/embedding providers — and is the only process that ever executes a pipeline. Both must be running for background work to complete: the API accepts and reports on tickets, the runtime consumes them.

The HTTP API is more than a health check. Besides GET /health/live and GET /health/ready, trialscribe_worker/api/jobs.py exposes a /jobs router:

MethodRoutePurpose
POST/jobsCreate a job ticket and enqueue it
GET/jobsList a conversation's tickets, newest first
GET/jobs/{id}Read one ticket, with live progress
POST/jobs/{id}/cancelCancel a queued ticket, or ask a running one to stop
GET/jobs/{id}/attemptsRead the latest per-section generation outcome
GET/jobs/{id}/rewrite-optionsRead the alternative drafts a rewrite job proposed
GET/jobs/readinessRead the latest protocol readiness snapshot
GET/jobs/usageRead token and cost totals for a conversation
GET/jobs/exportsList stored Word exports for a conversation
GET/jobs/exports/{id}/fileDownload one stored export

Every route reads X-TrialScribe-Account-ID and X-TrialScribe-Organization-ID, the same trusted headers the gateway writes for AI Engine calls, so the worker never re-verifies membership itself.

The worker does not own every table it touches. It owns jobs, evidence_chunks, provider_calls, section_generation_attempts, protocol_exports, and protocol_readiness_checks — all under the shared trialscribe PostgreSQL schema. It also reads and writes trialscribe.conversations, trialscribe.documents, and trialscribe.m11_sections, tables owned by other services' migrations, through plain SQL rather than by importing their application code.

Job kinds and the event flow

JobKind names seven kinds of work: probe, provider_probe, index_document, research_web, generate_sections, validate_readiness, and export_protocol. runtime/main.py maps each kind to a pipeline function from pipelines/. probe and provider_probe exist to exercise the runtime and the provider gateway end to end without touching real trial content; the other five are the product pipelines.

A ticket reaches the runtime one of two ways. A user action (through the gateway) calls POST /jobs, and JobService.request_job writes the job row and its job.requested event into the outbox in the same transaction — never publishing directly, since a crash between "write the ticket" and "publish the message" would otherwise either lose the message or hand out a ticket nobody committed. The other route is automatic: when AI Engine publishes document.uploaded, pipelines/document_events.py reacts by calling the same request_job to enqueue an index_document job; document.deleted instead removes that document's evidence chunks directly, with no job involved.

services/job_runner.py is what turns a job.requested record into a result. JobRunner.handle first claims the ticket — an update that only succeeds while the job's status is queued, running, or retrying, which is what makes a redelivered event harmless. Retries happen at two layers: the shared event consumer retries a failing handler up to max_delivery_attempts (3 by default) with jittered backoff before writing to a dead-letter topic, and each retry reclaims the ticket and increments its own attempt count. On the last attempt the job is marked failed with error code handler_failed (or cancelled, if a cancellation was requested) — written in the same transaction as the event consumer's own processed_events receipt, so the two can never disagree about whether the job's outcome is final.

Pipeline-specific failures are recorded at a finer grain: index_document writes a status and reason onto the document row itself (document could not be processed, contained no extractable text, or indexing failed), and generate_sections writes one row per section attempt with its own error code (missing_section, empty_output, provider_failed, revision_conflict, invalid_selection).

The provider gateway

Every chat and embedding call, from every pipeline, goes through providers/gateway.py — nothing calls a provider client directly. The gateway applies, in order: a per-operation concurrency limit (provider_max_concurrency, 8 by default) so one job cannot starve every other job's calls; an overall timeout (provider_timeout_seconds, 30s); a retry with full-jitter exponential backoff for a timeout, rate limit, or transport failure (provider_retry_attempts, 3); and a circuit breaker per operation that opens after 5 consecutive retryable failures and stays open for 30 seconds before allowing calls through again to test whether the provider has recovered. A non-retryable error (a bad request, an unsupported model) is not retried and does not count toward the breaker.

providers/factory.py builds the configured backend from WORKER_CHAT_PROVIDER and WORKER_EMBEDDING_PROVIDER: fake for both by default, deepseek (via the OpenAI-compatible SDK) for chat, and fastembed (a local sentence-embedding model) for embeddings. The fake chat provider echoes the last user message back, and the fake embedding provider returns a deterministic vector derived from a hash of the input text — the same text always embeds to the same vector, with no model file or network call. Both fakes accept an optional injected fault (a delay, an error to raise, and how many calls should fail before succeeding), configured through WORKER_FAKE_CHAT_FAULT_* environment variables — how a stress campaign exercises retries and circuit breaking without a real provider.

Every call is metered whether it succeeds or fails: token counts, latency, outcome, and a cost figure are recorded into trialscribe.provider_calls in their own short transaction, so a metering failure never undoes a provider call that already succeeded. Each chat request carries an idempotency key built from the job id, attempt number, and the specific call; a repeat of the exact same key is answered from the stored token and cost figures rather than billed twice. Embedding calls are never answered this way — every embed call reaches the provider.

RAG indexing and retrieval

retrieval/extraction.py turns stored file bytes into plain text: UTF-8 text and Markdown pass through as-is, PDFs are read with pypdf (an encrypted PDF is refused), and the structured trial-data JSON format is flattened into labelled lines (title, phase, disease area, interventions, inclusion/exclusion criteria). retrieval/chunking.py then splits that text into overlapping spans (1,200 characters with 200-character overlap by default), preferring to break on a paragraph, then a sentence, then a word boundary.

index_document runs extract, then chunk, then embed in batches of 32 through the gateway, then stores the batch. Storage is tenant-scoped and split across two stores: PostgreSQL writes the passage text, its character span, page number, and provenance — remaining the source of truth — while retrieval/chroma_index.py's ChromaIndex upserts only the vector and the chunk id into Chroma. Chroma organizes vectors into one collection per conversation; every write and query additionally carries an explicit organization/conversation filter, so a query can never cross a tenant boundary even if it somehow reached the wrong collection.

Retrieval mirrors that split: the query text is embedded through the same gateway, Chroma returns the nearest k chunk ids (8 by default) scoped to the tenant, and the matching rows are loaded from PostgreSQL by id. A chunk id Chroma still has but PostgreSQL no longer owns is silently dropped rather than returned, since PostgreSQL is what resolves a citation later.

Web research evidence

research_web searches two sources for a conversation-supplied query: retrieval/pubmed.py calls NCBI's search and fetch endpoints and parses the result into title, abstract, publication date, and a PubMed URL; and retrieval/tavily.py posts to Tavily's search API restricted to an allow-list of roughly a hundred medical, regulatory, and clinical research domains — fda.gov, nih.gov, cdc.gov, clinicaltrials.gov, nature.com, mayoclinic.org, sciencedirect.com, and similar. Tavily returns no results at all, rather than an error, when no API key is configured.

The pipeline runs both searches, then merges the hits: each result is reduced to a canonical URL, PubMed hits are kept unconditionally, web hits are kept only if their host is still on the allow-list, and duplicate URLs keep only the first hit seen. Each kept page is formatted into one passage, chunked, embedded, and stored through the same evidence index used for uploaded documents, under source_kind="web". Because web and PubMed passages land in the same evidence store as uploaded trial documents, section-drafting retrieval treats them uniformly — one search over a conversation's collection can return uploaded, PubMed, and web passages side by side.

Citation-backed generation and export

generate_sections drafts one or more of the 14 catalogued M11 section numbers. For each requested section it checks the section exists, is not already done, and that an optimistic-concurrency revision guard still matches — a mismatch is recorded as skipped, not retried. It retrieves evidence for the section, then prompts the model with a system message stating plainly that retrieved evidence and uploaded documents are untrusted data, never instruction, and that it may cite a passage only with a [cite:<uuid>] marker drawn from the evidence it was actually given. retrieval/citations.py then strips any citation marker whose id was not among the chunks retrieved for that call — a bound against the model citing an id it invented or remembered from elsewhere.

The same pipeline also serves a rewrite mode: given one section, an instruction, and an optional selection, it produces two alternative rewrites — one told to keep a similar length, one told to tighten the wording — without saving either; the caller chooses one through the conversation UI. Sections in a job succeed or fail independently, so a caller can re-request just the sections still empty rather than redo ones that already landed.

validate_readiness is a read-only scoring pass checking that all 14 sections exist, are done, and are non-empty, that no uploaded source is still pending or failed, and that no section's citations point at evidence no longer resolvable. It writes one snapshot row that both the readiness endpoint and export_protocol read back rather than recomputing.

export_protocol does not draft or edit any section text. It loads the latest readiness snapshot and refuses to export if none exists or if the conversation has had activity since the snapshot was computed; an export scoped to done-only sections additionally refuses unless the snapshot says the protocol is ready. It assembles a Word document with a title page, one heading per section, citation markers replaced by sequential numbers in first-appearance order, and a closing references section — stored and served back through GET /jobs/exports/{id}/file.

Running locally

Bootstrap the environment and infrastructure once, from the repository root:

./scripts.sh env
./scripts.sh install
./scripts.sh infra up
./scripts.sh db migrate

The worker needs both of its processes running. In separate terminals:

./scripts.sh run worker   # HTTP API on port 8004 (WORKER_PORT)
./scripts.sh run jobs     # Kafka consumer + pipelines — trialscribe_worker.runtime.main

WORKER_CHAT_PROVIDER and WORKER_EMBEDDING_PROVIDER default to fake in .env_example, so ./scripts.sh run jobs drafts sections, embeds text, and passes through the provider gateway's full retry and circuit-breaking logic without any external API key. To exercise the real chat model, set WORKER_CHAT_PROVIDER=deepseek and DEEPSEEK_API_KEY; to embed with a real local model, set WORKER_EMBEDDING_PROVIDER=fastembed. Web research needs its own keys regardless: TAVILY_API_KEY for website search and NCBI_API_KEY for PubMed.

./scripts.sh jobs test runs an isolated, disposable integration check of the background job runtime against its own Postgres/Redis/Kafka containers, then removes them. The job runtime also publishes Prometheus metrics on its own port (WORKER_JOBS_METRICS_PORT, 8006 by default), separate from the HTTP API's port.
